The problemปัญหา

Why bother with Clean Architecture?ทำไมต้องใช้ Clean Architecture?

Start with what goes wrong when business logic and infrastructure are tangled together.เริ่มจากสิ่งที่พังเมื่อ business logic ปนกับ infrastructure

Here's "register a customer" the way it's often first written — the rule, the database, and the web framework all in one class:นี่คือ "สมัครสมาชิก" แบบที่มักเขียนกันตอนแรก — กฎธุรกิจ, ฐานข้อมูล และ web framework รวมกันอยู่ในคลาสเดียว:

😵 tangled — controller does everythingพันกัน — controller ทำทุกอย่าง
⚠️ What hurts laterสิ่งที่จะเจ็บทีหลัง To unit-test the rule you must boot a DB and a mail server. The same "email must be unique" rule gets copy-pasted into every entry point. There's no obvious home for a rule, a use case, or a piece of presentation — everything piles up in the controller and grows into a big ball of mud as the team scales. จะ unit-test กฎ ต้องบูต DB และ mail server จริง กฎ "อีเมลห้ามซ้ำ" เดิมถูก copy-paste ไปทุกทางเข้า และไม่มี บ้าน ที่ชัดเจนให้กฎ, use case หรือส่วน presentation — ทุกอย่างกองอยู่ใน controller แล้วบวมเป็น big ball of mud เมื่อทีมโตขึ้น
✅ The Clean Architecture idea in one lineแนวคิด Clean Architecture ในบรรทัดเดียว Split the system into four concentric layers — Entities → Use Cases → Interface Adapters → Frameworks & Drivers — and enforce one rule: source-code dependencies point only inward. Every kind of code gets a named home, and the business core never imports a framework. แบ่งระบบเป็น 4 ชั้นซ้อนเป็นวง — Entities → Use Cases → Interface Adapters → Frameworks & Drivers — แล้วบังคับกฎข้อเดียว: dependency ของ source code ชี้เข้าด้านในเท่านั้น โค้ดทุกประเภทมีบ้านที่มีชื่อชัด และแก่นธุรกิจไม่เคย import framework

The four layers + the one rule4 ชั้น + กฎข้อเดียว

④Frameworks & DriversThe outermost detail — DB, web framework, Docker, the main. Thin glue you can swap.รายละเอียดนอกสุด — DB, web framework, Docker, main เป็น glue บางๆ ที่สลับได้
③Interface AdaptersControllers, presenters, gateways — reshape data between the inside and the outside.Controller, presenter, gateway — แปลงรูปข้อมูลระหว่างชั้นในกับชั้นนอก
②Use CasesApplication business rules — interactors that orchestrate entities for one scenario.Application business rules — interactor ที่ orchestrate entity ตาม scenario เดียว
①EntitiesEnterprise business rules — pure Kotlin, the slowest to change, aware of nothing outside.Enterprise business rules — Kotlin ล้วน เปลี่ยนช้าที่สุด ไม่รู้จักชั้นนอกเลย

▲ dependencies point inward — outer knows inner, never the reverse▲ dependency ชี้เข้าใน — ชั้นนอกรู้จักชั้นใน แต่ชั้นในไม่รู้จักชั้นนอก

◎ Core vocabularyคำศัพท์แกนหลัก

EntityEntity
Enterprise rules + the data they protect. Plain Kotlin value objects (Email, CustomerId) that guard their own invariants. No annotations, no DB.กฎระดับองค์กร + ข้อมูลที่มันปกป้อง เป็น value object Kotlin ล้วน (Email, CustomerId) ที่คุม invariant ของตัวเอง ไม่มี annotation ไม่มี DB
Use Case / InteractorUse Case / Interactor
One application scenario ("register a customer"). The interactor is the class that implements it; it orchestrates entities and output ports.หนึ่ง scenario ของแอป ("สมัครสมาชิก") interactor คือคลาสที่ implement มัน — orchestrate entity และ output port
Input boundaryInput boundary
An interface the use-case layer exposes for the outside to call (e.g. RegisterCustomer). Controllers depend on this, never on the interactor.interface ที่ชั้น use case เปิดให้ ภายนอกเรียก (เช่น RegisterCustomer) controller พึ่งอันนี้ ไม่พึ่ง interactor
Output port / GatewayOutput port / Gateway
An interface the use case needs from the world (e.g. CustomerGateway, Notifier). The interactor calls it; an adapter implements it.interface ที่ use case ต้องการ จากโลกภายนอก (เช่น CustomerGateway, Notifier) interactor เป็นคนเรียก, adapter เป็นคน implement
Interface AdapterInterface Adapter
Controllers, presenters and gateway implementations — they map between the inner models and outside shapes (JSON DTO, DB row).Controller, presenter และตัว implement gateway — ทำหน้าที่ แปลง ระหว่าง model ชั้นในกับรูปข้อมูลชั้นนอก (JSON DTO, DB row)

★ The one rule + how to read a boundaryกฎข้อเดียว + วิธีอ่าน boundary

★ The Dependency Ruleกฎ Dependency
Source-code arrows point inward only: frameworks → adapters → usecases → entities. Check it by reading imports — a file in entities/ or usecases/ must not import anything from adapters/ or frameworks/.ลูกศรของ source code ชี้ เข้าใน เท่านั้น: frameworks → adapters → usecases → entities ตรวจง่ายๆ จาก import — ไฟล์ใน entities/ หรือ usecases/ ต้องไม่ import อะไรจาก adapters/ หรือ frameworks/
Crossing a boundary (DIP)ข้ามเส้นชั้น (DIP)
When the core must drive something outward (save to a DB), it declares an interface inside and lets the outer layer implement it. Control flows out; the dependency still points in.เมื่อ core ต้องสั่งงานออกนอก (เซฟลง DB) มันประกาศ interface ไว้ ข้างใน แล้วให้ชั้นนอก implement — control flow วิ่งออก แต่ dependency ยังชี้เข้า
Data across boundariesข้อมูลข้ามชั้น
Pass plain models / DTOs across layers — RegisterInput, RegisterOutput — never hand a raw entity or DB row across. Each side stays free to change.ส่งข้อมูลข้ามชั้นเป็น model / DTO ง่ายๆ — RegisterInput, RegisterOutput — อย่าส่ง entity หรือ DB row ดิบข้ามไป แต่ละฝั่งจึงเปลี่ยนได้อิสระ
Why it pays offทำไมถึงคุ้ม
Every kind of code has one named home, so a new dev knows exactly where things live. Test the core with fake gateways (fast). Swap DB/web by writing a new adapter (safe).โค้ดทุกประเภทมีบ้านที่มีชื่อชัด คนใหม่จึงรู้ทันทีว่าอะไรอยู่ตรงไหน เทส core ด้วย gateway ปลอม (เร็ว) เปลี่ยน DB/web ด้วยการเขียน adapter ใหม่ (ปลอดภัย)
The system we buildระบบที่เราจะสร้าง

1M customers, 1K products — why scale stays in the outer layersลูกค้า 1M, สินค้า 1K — ทำไม scale อยู่แค่ชั้นนอก

👤

Customers — 1,000,000ลูกค้า — 1,000,000

Write- and auth-heavy, must scale out. The CustomerGateway output port lets you start on one Postgres and move to a sharded store later — entities and use cases untouched.หนักด้าน write และ auth ต้อง scale out, output port CustomerGateway ทำให้เริ่มที่ Postgres เดียวแล้วย้ายไป store แบบ shard ทีหลังได้ — entity และ use case ไม่ต้องแตะ

📦

Products — 1,000สินค้า — 1,000

Tiny and read-heavy. The whole catalog fits in RAM, so a cached gateway behind the ProductGateway port is a no-brainer — same port, different adapter.เล็กและหนักด้าน read ทั้ง catalog ใส่ใน RAM ได้ ดังนั้น gateway แบบ cache หลัง port ProductGateway คือคำตอบ — port เดิม คนละ adapter

🗂️

Categories — 100หมวดหมู่ — 100

Practically static. Group products in memory; refresh on a timer. The use cases never learn whether data came from a DB or a cache.แทบไม่เปลี่ยน จัดกลุ่มสินค้าในหน่วยความจำ แล้ว refresh ตามเวลา use case ไม่มีวันรู้ว่าข้อมูลมาจาก DB หรือ cache

🧭 The lessonบทเรียน Scale decisions (shard the customers, cache the catalog) are Frameworks & Drivers / adapter decisions. They live in the outer two layers — so the Entities and Use Cases of "register a customer" and "list products" stay identical whether you have 1K customers or 100M. การตัดสินใจเรื่อง scale (shard ลูกค้า, cache catalog) คือการตัดสินใจระดับ Frameworks & Drivers / adapter มันอยู่ใน 2 ชั้นนอก — Entities และ Use Cases ของ "สมัครสมาชิก" และ "ดูสินค้า" จึงเหมือนเดิมไม่ว่าจะมีลูกค้า 1K หรือ 100M

The composition root — wiringcomposition root — ประกอบร่าง

In the Frameworks & Drivers layer, one @Factory builds each framework-free interactor from its gateways and exposes it by its input-boundary type. Day-to-dayใช้งานจริง

Practices & naming — and the trapsวิธีปฏิบัติ & การตั้งชื่อ — และกับดัก

✅ Doควรทำ

  • Put each kind of code in its layer: entities/, usecases/, adapters/, frameworks/.วางโค้ดแต่ละประเภทในชั้นของมัน: entities/, usecases/, adapters/, frameworks/
  • Make controllers depend on the input boundary, never the interactor.ให้ controller พึ่ง input boundary ไม่ใช่ interactor
  • Keep use-case models (RegisterInput/Output) separate from web DTOs; map between them in the controller.แยก use-case model (RegisterInput/Output) ออกจาก web DTO แล้วแปลงกันใน controller
  • Let entities guard their own invariants (value objects like Email).ให้ entity คุม invariant ของตัวเอง (value object เช่น Email)

🚫 Don't (junior traps)อย่าทำ (กับดัก junior)

  • Don't import anything from adapters/ or frameworks/ inside entities/ or usecases/.อย่า import อะไรจาก adapters/ หรือ frameworks/ เข้าไปใน entities/ หรือ usecases/
  • Don't return a CustomerRow / JPA entity from a gateway — return a domain entity.อย่าคืน CustomerRow / JPA entity จาก gateway — ให้คืน domain entity
  • Don't let a web DTO leak into the use case (or annotate use-case models with @Schema).อย่าให้ web DTO หลุดเข้าไปใน use case (หรือใส่ @Schema ใน use-case model)
  • Don't add four strict layers + mappers to a tiny CRUD app — that's just ceremony.อย่าซอย 4 ชั้นเข้ม + mapper ให้แอป CRUD เล็กๆ — มันคือพิธีกรรมเปล่าๆ
📁 A naming convention that scalesแนวตั้งชื่อที่ใช้ได้ระยะยาว entities/ (① enterprise rules) · usecases/ + usecases/port/ (② app rules + boundaries/gateways) · adapters/web, adapters/persistence, adapters/notification (③ interface adapters) · frameworks/ + frameworks/config (④ main + composition root). One folder = one layer. entities/ (① กฎระดับองค์กร) · usecases/ + usecases/port/ (② กฎระดับแอป + boundary/gateway) · adapters/web, adapters/persistence, adapters/notification (③ interface adapter) · frameworks/ + frameworks/config (④ main + composition root) — หนึ่งโฟลเดอร์ = หนึ่งชั้น
⚖️ Clean vs Hexagonal — the same domain, two structuresClean vs Hexagonal — โดเมนเดียว สองโครงสร้าง Compared to the Hexagonal page: Clean splits the use case into an input boundary + interactor, gives it its own request/response models (separate from web DTOs), names outbound ports gateways, and folders the code into four named layers. Hexagonal keeps one RegisterCustomer class and a flatter domain/ + infra/. Both obey the exact same Dependency Rule — Clean just makes the boundaries more concrete. เทียบกับ หน้า Hexagonal: Clean แยก use case เป็น input boundary + interactor ให้มี request/response model ของตัวเอง (แยกจาก web DTO) เรียก port ขาออกว่า gateway และจัดโค้ดเป็น 4 ชั้นที่มีชื่อ ส่วน Hexagonal ใช้คลาส RegisterCustomer เดียวและโครง domain/ + infra/ ที่แบนกว่า ทั้งคู่เคารพ Dependency Rule เดียวกันเป๊ะ — Clean แค่ทำ boundary ให้เป็นรูปธรรมกว่า

Glossary, FAQ & a first-day checklistGlossary, FAQ & checklist วันแรก

Entity
Enterprise business rules + the data they protect — the innermost circle.กฎระดับองค์กร + ข้อมูลที่มันปกป้อง — วงในสุด
Use Case / Interactor
Application business rules; the interactor is the class implementing one scenario.กฎระดับแอป; interactor คือคลาสที่ implement หนึ่ง scenario
Input boundary
The interface a controller calls; the interactor implements it.interface ที่ controller เรียก; interactor เป็นคน implement
Output port / Gateway
An interface the use case needs (DB, email); an adapter implements it.interface ที่ use case ต้องการ (DB, email); adapter เป็นคน implement
Interface Adapter
Controller / presenter / gateway impl — maps between inner and outer shapes.Controller / presenter / ตัว implement gateway — แปลงรูประหว่างชั้นในกับชั้นนอก
Frameworks & Drivers
The outermost layer — DB, web, the main; thin, swappable glue.ชั้นนอกสุด — DB, web, main; เป็น glue บางๆ ที่สลับได้
Composition root
The single place that wires interactors to gateways (a @Factory).จุดเดียวที่ประกอบ interactor เข้ากับ gateway (เช่น @Factory)
Why an input boundary AND an interactor — isn't that two files for one thing?ทำไมต้องมีทั้ง input boundary และ interactor — มันคือ 2 ไฟล์เพื่อของชิ้นเดียวไม่ใช่เหรอ?

The interface (boundary) is what the controller compiles against; the interactor is the swappable implementation. It lets you fake the use case in adapter tests, expose two implementations, and keeps the dependency pointing inward. For a tiny app it can feel like ceremony — Hexagonal collapses them into one class.interface (boundary) คือสิ่งที่ controller compile ด้วย ส่วน interactor คือ implementation ที่สลับได้ ทำให้ fake use case ในเทส adapter ได้, มี implementation สองตัวได้ และคง dependency ให้ชี้เข้าใน สำหรับแอปเล็กๆ อาจรู้สึกเป็นพิธีกรรม — Hexagonal ยุบทั้งคู่เป็นคลาสเดียว

Do I really need separate request/response models from the web DTOs?ต้องแยก request/response model จาก web DTO จริงๆ เหรอ?

It's Clean's recommendation, and it pays off when the use case has more than one driver (REST + a CLI + a queue) or when the JSON shape diverges from what the use case needs. For a single REST entry point, some teams reuse the DTO — a pragmatic shortcut, but you lose the firewall.เป็นคำแนะนำของ Clean และคุ้มเมื่อ use case มี driver มากกว่าหนึ่ง (REST + CLI + queue) หรือเมื่อรูป JSON ต่างจากที่ use case ต้องการ ถ้ามีทางเข้า REST ทางเดียว บางทีมใช้ DTO ซ้ำ — เป็นทางลัด pragmatic แต่จะเสีย firewall ไป

Where does validation go — controller or core?validation อยู่ตรงไหน — controller หรือ core?

Shape checks (is the JSON well-formed, fields present?) sit on the web DTO (@NotBlank, @Size). Business rules (email must be a valid email and unique) belong in the entity and the interactor, where they're tested without a web layer.การตรวจรูปแบบ (JSON ถูกโครงสร้าง, มีฟิลด์ครบไหม) อยู่ที่ web DTO (@NotBlank, @Size) ส่วน กฎธุรกิจ (อีเมลต้องถูกรูปแบบและห้ามซ้ำ) อยู่ใน entity และ interactor ที่เทสได้โดยไม่ต้องมีชั้นเว็บ

Is this the same as Hexagonal?อันนี้เหมือน Hexagonal ไหม?

Same goal, different emphasis. Hexagonal focuses on the in/out boundary (ports & adapters); Clean adds named concentric layers and more explicit boundaries/models. Uncle Bob calls Clean a superset that integrates Hexagonal, Onion, DCI and BCE. See the comparison.เป้าหมายเดียวกัน เน้นต่างกัน Hexagonal เน้นขอบ in/out (port & adapter) ส่วน Clean เพิ่มชั้นซ้อนที่มีชื่อและ boundary/model ที่ชัดกว่า Uncle Bob บอกว่า Clean เป็น superset ที่รวม Hexagonal, Onion, DCI, BCE ดู ตารางเทียบ

🚀 First-day checklistchecklist วันแรก
  • Find entities/ — read the value objects and rules first (the innermost circle).หา entities/ — อ่าน value object และกฎก่อน (วงในสุด)
  • In usecases/, read each input boundary + its interactor; in usecases/port/, the gateways.ใน usecases/ อ่าน input boundary + interactor ของมัน; ใน usecases/port/ ดู gateway
  • For each gateway, find its implementation in adapters/.แต่ละ gateway หา implementation ของมันใน adapters/
  • Open the composition root (frameworks/config/Beans.kt) to see how it's wired.เปิด composition root (frameworks/config/Beans.kt) เพื่อดูว่าประกอบกันยังไง
  • Write your first feature inside-out: entity → port → boundary → interactor → adapter → test.เขียนฟีเจอร์แรกแบบ inside-out: entity → port → boundary → interactor → adapter → test
