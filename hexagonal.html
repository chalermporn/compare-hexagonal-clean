The problemปัญหา

Why bother with Hexagonal?ทำไมต้องใช้ Hexagonal?

Start with what goes wrong when business logic and infrastructure are tangled together.เริ่มจากสิ่งที่พังเมื่อ business logic ปนกับ infrastructure

Here's "register a customer" the way it's often first written — the rule, the database, and the web framework all in one class:นี่คือ "สมัครสมาชิก" แบบที่มักเขียนกันตอนแรก — กฎธุรกิจ, ฐานข้อมูล และ web framework รวมกันอยู่ในคลาสเดียว:

😵 tangled — controller does everythingพันกัน — controller ทำทุกอย่าง
⚠️ What hurts laterสิ่งที่จะเจ็บทีหลัง To unit-test the rule you must boot a DB and a mail server. To move from Postgres to a sharded store (you have 1M customers!) you rewrite the controller. The same "email must be unique" rule gets copy-pasted into every entry point (REST, a CLI importer, a Kafka consumer). The business logic is trapped inside infrastructure. จะ unit-test กฎ ต้องบูต DB และ mail server จริง จะย้ายจาก Postgres ไป store แบบ shard (มีลูกค้า 1M!) ต้องรื้อ controller กฎ "อีเมลห้ามซ้ำ" เดิมถูก copy-paste ไปทุกทางเข้า (REST, ตัว import CLI, Kafka consumer) — business logic ถูก ขัง อยู่ใน infrastructure
✅ The Hexagonal idea in one lineแนวคิด Hexagonal ในบรรทัดเดียว Put the business rules in a core that talks to the outside world only through interfaces it owns (ports). Everything technical — DB, web, email — becomes a replaceable adapter at the edge. เอา business rule ไว้ใน core ที่คุยกับโลกภายนอกผ่าน interface ที่ core เป็นเจ้าของ (port) เท่านั้น ส่วนเรื่องเทคนิคทั้งหมด — DB, web, email — กลายเป็น adapter ที่ขอบซึ่งสลับได้

The system we buildระบบที่เราจะสร้าง

1M customers, 1K products — why scale shapes the edgesลูกค้า 1M, สินค้า 1K — ทำไม scale กำหนดที่ "ขอบ"

👤

Customers — 1,000,000ลูกค้า — 1,000,000

Write- and auth-heavy, must scale out. The CustomerRepository port lets you start on one Postgres and move to a sharded store later — core untouched.หนักด้าน write และ auth ต้อง scale out, port CustomerRepository ทำให้เริ่มที่ Postgres เดียวแล้วย้ายไป store แบบ shard ทีหลังได้ — core ไม่ต้องแตะ

📦

Products — 1,000สินค้า — 1,000

Tiny and read-heavy. The whole catalog fits in RAM, so a cached adapter behind the ProductCatalog port is a no-brainer — same port, different adapter.เล็กและหนักด้าน read ทั้ง catalog ใส่ใน RAM ได้ ดังนั้น adapter แบบ cache หลัง port ProductCatalog คือคำตอบ — port เดิม คนละ adapter

🗂️

Categories — 100หมวดหมู่ — 100

Practically static. Group products in memory; refresh on a timer. The core's use cases never learn whether data came from a DB or a cache.แทบไม่เปลี่ยน จัดกลุ่มสินค้าในหน่วยความจำ แล้ว refresh ตามเวลา use case ใน core ไม่มีวันรู้ว่าข้อมูลมาจาก DB หรือ cache

🧭 The lessonบทเรียน Scale decisions (shard the customers, cache the catalog) are infrastructure decisions. In Hexagonal they live entirely in adapters — so the rules of "register a customer" and "place an order" stay identical whether you have 1K customers or 100M. การตัดสินใจเรื่อง scale (shard ลูกค้า, cache catalog) คือการตัดสินใจระดับ infrastructure ใน Hexagonal มันอยู่ใน adapter ทั้งหมด — กฎของ "สมัครสมาชิก" และ "สั่งซื้อ" จึงเหมือนเดิมไม่ว่าจะมีลูกค้า 1K หรือ 100M

Practices & naming — and the trapsวิธีปฏิบัติ & การตั้งชื่อ — และกับดัก

✅ Doควรทำ

  • Name ports in business language: CustomerRepository, Notifier — not PostgresDao.ตั้งชื่อ port เป็น ภาษาธุรกิจ: CustomerRepository, Notifier — ไม่ใช่ PostgresDao
  • Keep the port in the core, the adapter in infra/.เก็บ port ไว้ ใน core ส่วน adapter อยู่ใน infra/
  • Map DB rows / DTOs to domain inside the adapter.แปลง row/DTO เป็น domain ภายใน adapter
  • Define a port only when you have a real reason to swap or fake it.สร้าง port เมื่อมี เหตุผลจริง ที่จะสลับหรือทำ fake เท่านั้น

🚫 Don't (junior traps)อย่าทำ (กับดัก junior)

  • Don't import anything from infra/ inside the core.อย่า import อะไรจาก infra/ เข้าไปใน core
  • Don't return a CustomerRow / JPA entity from a port — return domain.อย่าคืน CustomerRow / JPA entity จาก port — ให้คืน domain
  • Don't make a port that just mirrors one DB table (save/find 1:1) with no domain meaning.อย่าสร้าง port ที่แค่สะท้อนตาราง DB หนึ่งตาราง (save/find 1:1) โดยไม่มีความหมายเชิง domain
  • Don't put if-business-rules inside a controller or adapter.อย่าเอา if ที่เป็นกฎธุรกิจไปไว้ใน controller หรือ adapter
📁 A naming convention that scalesแนวตั้งชื่อที่ใช้ได้ระยะยาว domain/ (entities) · domain/port/ (interfaces) · application/ (use cases) · infra/web, infra/persistence, infra/email (adapters) · infra/config (factories). One folder = one job. domain/ (entity) · domain/port/ (interface) · application/ (use case) · infra/web, infra/persistence, infra/email (adapter) · infra/config (factory) — หนึ่งโฟลเดอร์ = หนึ่งหน้าที่

Isn't a port just an interface? Why the fancy name?port ก็แค่ interface ไม่ใช่เหรอ ทำไมต้องตั้งชื่อหรู?

Yes, technically it's a Kotlin interface. "Port" tells you where it lives (the core's boundary) and who owns it (the core, not the adapter). The name encodes a rule, not a new language feature.ใช่ ทางเทคนิคมันคือ interface ของ Kotlin คำว่า "port" บอกว่ามันอยู่ ตรงไหน (ขอบของ core) และ ใคร เป็นเจ้าของ (core ไม่ใช่ adapter) ชื่อนี้เข้ารหัสกฎไว้ ไม่ใช่ฟีเจอร์ใหม่ของภาษา

Do I need a port for everything?ต้องมี port ให้ทุกอย่างไหม?

No. Create a port when you'll swap the implementation, fake it in tests, or cross a real boundary (DB, network, clock). A pure helper function needs no port.ไม่ สร้าง port เมื่อจะ สลับ implementation, ทำ fake ในเทส หรือข้ามขอบจริง (DB, network, clock) ฟังก์ชัน helper ล้วนๆ ไม่ต้องมี port

Where does validation go — controller or core?validation อยู่ตรงไหน — controller หรือ core?

Shape checks (is this JSON well-formed?) can sit at the controller. Business rules (email must be unique, order total ≥ 0) belong in the domain/use case, where they're tested without a web layer.การตรวจรูปแบบ (JSON ถูกโครงสร้างไหม) อยู่ที่ controller ได้ ส่วน กฎธุรกิจ (อีเมลห้ามซ้ำ, ยอดรวม ≥ 0) ต้องอยู่ใน domain/use case ที่เทสได้โดยไม่ต้องมีชั้นเว็บ

Is this the same as Clean Architecture?อันนี้เหมือน Clean Architecture ไหม?

Same goal, different emphasis. Hexagonal focuses on the in/out boundary (ports & adapters); Clean adds named concentric layers. See the comparison.เป้าหมายเดียวกัน เน้นต่างกัน Hexagonal เน้นขอบ in/out (port & adapter) ส่วน Clean เพิ่มชั้นซ้อนที่มีชื่อชัด ดู ตารางเทียบ
