Hexagonal vs Clean

Two architectures with the same goal — keep business logic independent of infrastructure and force every dependency to point inward toward the core. They differ only in perspective and number of layers. สองสถาปัตยกรรมที่มีเป้าหมายเดียวกัน — แยก business logic ออกจาก infrastructure และบังคับให้ dependency ทุกเส้นชี้เข้าหา core เสมอ ต่างกันแค่ "มุมมอง" และ "จำนวนชั้น"

Ports & Adapters

Hexagonal Architecture

Coined by Alistair Cockburn (~2005) — it focuses on the edges of the system. The core talks to the outside world through a Port (the contract) and an Adapter (the implementation).คิดค้นโดย Alistair Cockburn (~2005) — โฟกัสที่ "ขอบ" ของระบบ core คุยกับโลกภายนอกผ่าน Port (สัญญา) และ Adapter (ตัว implement)

  • Driving side (left/top) — who calls us: REST, CLI, TestDriving side (ซ้าย/บน) — ใครเรียกเรา: REST, CLI, Test
  • Driven side (right/bottom) — who we call: DB, Email, QueueDriven side (ขวา/ล่าง) — เราเรียกใคร: DB, Email, Queue
  • Swap any adapter freely — the core never knowsเปลี่ยน adapter ได้อิสระ core ไม่รู้เรื่อง
  • No fixed number of inner layers — highly flexibleไม่บังคับจำนวนชั้นภายใน — ยืดหยุ่นสูง

Where they came fromที่มา

A short history of both patternsประวัติที่มาของทั้งสอง pattern

Neither appeared from nowhere — they're one lineage, each idea building on the last toward the same goal: a framework-free core.ทั้งคู่ไม่ได้เกิดมาลอยๆ — มันคือสายวิวัฒนาการเดียวกันที่ต่อยอดกันมาเรื่อยๆ สู่เป้าหมายเดียวกัน: core ที่ปลอด framework

Hexagonal lineสาย Hexagonal Clean lineสาย Clean Influencesแนวคิดต้นธาร
1992
BCE — Boundary · Control · Entity Ivar Jacobson · OOSE

Jacobson — the “father of use cases” and later a driving force behind UML and the Rational Unified Process — sorted objects into three stereotypes in his book Object-Oriented Software Engineering: Boundary (talks to actors), Entity (long-lived business data) and Control (coordinates one use case). Grouping objects by what makes them change — UI churn vs. business rules — is the earliest ancestor of keeping the core away from I/O.Jacobson — “บิดาแห่ง use case” และต่อมาเป็นกำลังหลักของ UML กับ Rational Unified Process — จัด object เป็น 3 ประเภทในหนังสือ Object-Oriented Software Engineering: Boundary (คุยกับ actor), Entity (ข้อมูลธุรกิจที่อยู่ยาว) และ Control (ประสานงานหนึ่ง use case). การจัดกลุ่ม object ตาม “อะไรทำให้มันเปลี่ยน” — เรื่อง UI vs. กฎธุรกิจ — คือบรรพบุรุษเก่าสุดของการกัน core ออกจาก I/O

2003
Domain-Driven Design Eric Evans · the “blue book”

Evans saw complex systems rot whenever the code drifted away from the business it served. His answer: put the domain model at the heart of design and bind developers and domain experts to one shared Ubiquitous Language. The building blocks he named — Entities, Value Objects, Repositories, Aggregates — and his rule to isolate the domain layer became exactly the inner rings both later patterns work to protect.Evans เห็นว่าระบบซับซ้อนจะ “ผุพัง” ทุกครั้งที่โค้ดหลุดจากธุรกิจที่มันรองรับ. คำตอบของเขาคือวาง domain model ไว้เป็นหัวใจ ของการออกแบบ และมัดนักพัฒนากับผู้เชี่ยวชาญโดเมนไว้ด้วย Ubiquitous Language เดียวกัน. building block ที่เขาตั้งชื่อ — Entity, Value Object, Repository, Aggregate — กับกฎให้แยกชั้นโดเมนออกมา กลายเป็นวงในที่ทั้งสอง pattern พยายามปกป้องนั่นเอง

2005
Hexagonal — Ports & Adapters ⬡ Hexagonal Alistair Cockburn

Cockburn — a use-case authority and one of the 17 signatories of the Agile Manifesto — kept hitting the same bug: business logic leaking into the UI, and an app you couldn’t test without a real database. His stated goal was to “allow an application to be driven equally by users, programs, automated tests or scripts, and to be developed and tested in isolation from its eventual run-time devices and databases.” A port is the contract the core owns; an adapter plugs the real world into it. The hexagon was just a drawing with room for several ports — so he later preferred the clearer name “Ports & Adapters.”Cockburn — ผู้เชี่ยวชาญ use case และ 1 ใน 17 ผู้ลงนาม Agile Manifesto — เจอบั๊กเดิมซ้ำๆ: business logic รั่วเข้า UI และแอปที่เทสไม่ได้ถ้าไม่มี DB จริง. เป้าหมายที่เขาประกาศไว้คือ “ให้แอปถูกขับได้เท่าๆ กันไม่ว่าจะจาก user, โปรแกรม, automated test หรือ script และพัฒนา/เทสได้โดยแยกขาดจากอุปกรณ์และฐานข้อมูลปลายทาง”. port คือสัญญาที่ core เป็นเจ้าของ ส่วน adapter คือตัวเสียบโลกจริงเข้ามา. รูปหกเหลี่ยมเป็นแค่ภาพที่มีที่ว่างพอวาง port หลายตัว เขาจึงเปลี่ยนมาใช้ชื่อที่ชัดกว่าว่า “Ports & Adapters”

2008
Onion Architecture Jeffrey Palermo · .NET

Palermo, a .NET architect, attacked classic N-tier, where every layer ultimately depends on the database sitting at the bottom. In a series of blog posts he turned the stack inside-out: the domain model sits at the centre, infrastructure moves to the outermost ring, and every dependency points inward through interfaces (Inversion of Control). It’s the visual step from Hexagonal’s flat edges to Clean’s concentric circles.Palermo สถาปนิกสาย .NET โจมตี N-tier แบบเดิมที่ทุกชั้นสุดท้ายไปพึ่ง ฐานข้อมูลที่ก้นสุด. เขาเขียนบล็อกชุดหนึ่งกลับด้านกองชั้นนั้น: วาง domain model ไว้ตรงกลาง, ดัน infrastructure ออกไปวงนอกสุด, และให้ทุก dependency ชี้เข้าด้านในผ่าน interface (Inversion of Control). เป็นก้าวเชิงภาพจาก “ขอบแบนๆ” ของ Hexagonal ไปสู่ “วงกลมซ้อน” ของ Clean

2012
Clean Architecture ◎ Clean Robert C. Martin (Uncle Bob)

Martin — a co-author of the Agile Manifesto and the popularizer of the SOLID principles — noticed that Hexagonal, Onion, BCE and DCI were all telling the same story in different words. In the blog post The Clean Architecture (Aug 2012) he merged them into one diagram: four concentric layers — Entities → Use Cases → Interface Adapters → Frameworks & Drivers — held together by a single law, The Dependency Rule: source-code dependencies may point only inward.Martin — ผู้ร่วมเขียน Agile Manifesto และผู้ทำให้หลัก SOLID แพร่หลาย — สังเกตว่า Hexagonal, Onion, BCE และ DCI ล้วน เล่าเรื่องเดียวกันด้วยคำต่างกัน. ในบล็อก The Clean Architecture (ส.ค. 2012) เขารวมทั้งหมดเป็นภาพเดียว: 4 วงซ้อน — Entities → Use Cases → Interface Adapters → Frameworks & Drivers — ยึดไว้ด้วยกฎข้อเดียวคือ The Dependency Rule: source-code dependency ชี้เข้าด้านในได้เท่านั้น

2017
Clean Architecture — the book Robert C. Martin

Clean Architecture: A Craftsman’s Guide to Software Structure and Design grows the 2012 post into a full treatise — tying the layers back to SOLID and component-cohesion principles, and sharpening the line between policy (what the software does) and detail (how it’s delivered: the web, the DB, the framework).หนังสือ Clean Architecture: A Craftsman’s Guide to Software Structure and Design ขยายบล็อกปี 2012 เป็นตำราเต็มเล่ม — ผูกชั้นต่างๆ กลับเข้ากับหลัก SOLID และ component cohesion และลากเส้นแบ่งให้คมระหว่าง policy (ซอฟต์แวร์ทำอะไร) กับ detail (ส่งมอบอย่างไร: web, DB, framework)

2024
Hexagonal — the book A. Cockburn & J. M. Garrido de Paz

For nearly two decades the pattern lived mostly in a wiki article and conference talks. In April 2024 Cockburn, together with Juan Manuel Garrido de Paz, finally published the definitive book — pinning down the canonical definition and clearing up years of “but how many sides?” misreadings of the hexagon.เกือบสองทศวรรษที่ pattern นี้อยู่แค่ในบทความวิกิกับ talk ตามงานสัมมนา. เมษายน 2024 Cockburn ร่วมกับ Juan Manuel Garrido de Paz ออกหนังสือฉบับสมบูรณ์เสียที — ปักนิยามมาตรฐานและเคลียร์ความเข้าใจผิดเรื่อง “ตกลงมันกี่ด้าน?” ของรูปหกเหลี่ยมที่สะสมมาหลายปี

In short: Hexagonal drew the boundary, Onion bent it into rings, and Clean wrote down the rules — so Clean can be read as a stricter superset of Hexagonal.สรุปสั้นๆ: Hexagonal ขีดเส้นขอบ, Onion ดัดให้เป็นวง, แล้ว Clean เขียนกฎลงเป็นลายลักษณ์ — มองได้ว่า Clean คือ superset ที่เข้มงวดกว่าของ Hexagonal

Testing strategyกลยุทธ์การเทส

Because the core depends only on ports, you can test it with a fake adapter — no DB, no HTTP, milliseconds fast.เพราะ core พึ่งแค่ port จึงเทสด้วย adapter ปลอมได้ — ไม่ต่อ DB ไม่ต่อ HTTP เร็วระดับมิลลิวินาที

  • Unit (most) — core + in-memory adapter, no real I/OUnit (เยอะสุด) — core + in-memory adapter ไม่แตะ I/O จริง
  • Integration — the real adapter (Postgres, HTTP) against its portIntegration — adapter จริง (Postgres, HTTP) เทียบกับ port
  • E2E (fewest) — the whole system end to endE2E (น้อยสุด) — ทั้งระบบ end-to-end
  • Swapping a port for a fake makes the core 100% testableสลับ port เป็นของปลอมได้ → core เทสได้ 100%

Watch outระวัง

Common mistakesข้อผิดพลาดที่พบบ่อย

⚠️

Domain leaks outDomain รั่วออกไป

Importing a DB/framework library inside an entity or use case — the core is no longer pure.เผลอ import library ของ DB/framework เข้าไปใน entity หรือ use case — core เลิกบริสุทธิ์ทันที

🧱

Anemic coreCore กลวง

Business rules pile up in controllers/services while entities become dumb data bags.logic ไปกองใน controller/service ส่วน entity กลายเป็นแค่ถุงใส่ข้อมูล

🪆

Over-engineeringซอยชั้นเกินจำเป็น

A small CRUD app split into four strict layers — more ceremony than value.แอป CRUD เล็กๆ แต่ซอย 4 ชั้นเข้ม จนเขียนช้ากว่าประโยชน์ที่ได้

🔁

Mapping overloadMapping ล้นมือ

Converting DTO ↔ Entity ↔ Model through every layer until it hurts (Clean especially).แปลง DTO ↔ Entity ↔ Model ทุกชั้นจนเหนื่อย (เจอบ่อยใน Clean)

Be pragmaticใช้ให้พอดี

When NOT to — and how to adopt graduallyเมื่อไหร่ไม่ควรใช้ — และ adopt ทีละขั้น

🚫 Likely overkill when…อาจเกินจำเป็นเมื่อ…

  • It's mostly plain CRUD with little logicเป็น CRUD ล้วน logic แทบไม่มี
  • A prototype / PoC that may be thrown awayprototype / PoC ที่อาจถูกทิ้ง
  • A tiny team / very short-lived projectทีมเล็กมาก / โปรเจกต์อายุสั้น
  • A simple script or one-off jobสคริปต์ง่ายๆ หรืองานครั้งเดียวจบ

✅ Adopt one step at a timeadopt ทีละขั้น

  • Start with one important Port (e.g. the DB)เริ่มจาก Port สำคัญตัวเดียว (เช่น DB)
  • Pull the use case out of the controllerดึง use case ออกจาก controller
  • Add layers only as the domain growsค่อยเพิ่มชั้นเมื่อ domain โตขึ้น
  • No need for all four layers on day oneไม่ต้องมีครบ 4 ชั้นตั้งแต่วันแรก
